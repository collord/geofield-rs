# web2 — two-wasm scale benchmark + worker-driven viewer

A throughput harness for the two-wasm split (EUPL kernel + BSD engine) on a realistic
faulted, multi-series scenario at borehole scale. It loads both wasm modules, fits the
stack across the module boundary, and times fit + octree meshing while counting the
per-sample `gf_eval` calls that cross the boundary — then renders the model in 3D.

## Architecture: a solver worker keeps the UI live

The heavy wasm work (a ~40 s full fit, multi-second deep meshes) runs in a **web worker**,
not on the UI thread — so the page never freezes and a real status stream is possible:

- `worker.ts` owns BOTH wasm instances + the kernel-bridge, runs the fit + mesh, and
  **streams** typed events (`protocol.ts`): phase/progress, per-series fit timings as each
  lands, each contact surface **as it is meshed** (transferred zero-copy), depth-sweep
  rows, and the final stats.
- `main.ts` (UI thread) spawns the worker, renders the live status bar + tables, and adds
  surfaces to the three.js scene **progressively** as they arrive. The fit runs with the
  page fully responsive (the progress bar animates during the 40 s fit — it would be frozen
  solid on the main thread).
- **Cancel** is a hard `worker.terminate()` + respawn: a single fit is one uninterruptible
  wasm call, so killing the worker is the only way to stop mid-fit — and it is instant.
  The cost is a ~1 s cold wasm re-init on the next run, which is accepted.
- Surfaces are meshed and streamed **before** the timing sweep, so the geology appears as
  soon as the (fast, decimated) fit completes rather than after the whole benchmark.
- A faulted contact is meshed **per fault block** (`series → block → interface`), matching
  the `web/` harness: each block's sheet is contoured from that block's own smooth field and
  cut flush at the fault plane, so the offset reads as two clean sheets instead of one
  surface stretched across the discontinuity. `WasmStack.mesh_series_block_interface` /
  `series_block_count` back this; a non-faulted series is a single block (the whole domain).
- **Surfaces: contacts / closed solids** toggles the surface representation. *Contacts* are
  open sheets (one per interface); an eroded contact ends SHORT of the erosion surface because
  the cut edge is a dropped cap face (open-sheet view). *Closed solids* are watertight
  lithology-unit slabs (one per unit) capped by the box, the fault, AND every younger erosion
  — so an eroded unit DAYLIGHTS against the erosion surface instead of stopping short.
  `WasmStack.mesh_series_block_unit_solid` / `block_unit_count` back this. The toggle sends a
  `remesh` command that re-meshes the already-fitted stack (no refit — instant fit, ~seconds
  to re-mesh) rather than re-running the whole pipeline.

## The scenario

Generated by `gen/generate_scenario.py` (oldest → newest):

- **3 intact sedimentary contacts** (~400 ft apart, gently undulating) — one conformable
  series, 3 interface ids / 4 lithology units.
- an **erosional surface** dipping ~10° with **basalt** filling above it — a younger
  *Erode* series.
- a **late fault** (strike 20°, dip 80°, **100 ft down-to-the-east**) applied to both
  series (it post-dates everything).
- **3000 vertical boreholes** on a 300 ft grid jittered by N(0, 40 ft), each logging every
  contact it crosses → ~9000 sediment + ~3000 basalt surface points.

> Scale note: 3000 holes on a *literal* 300 ft grid is only 100 holes (a 3000 ft square).
> To honor the 3000-hole target the generator sizes the map to ~16,500 ft and rescales the
> geology to fit (the absolute 400 ft thickness / 100 ft offset are preserved).

## Run

```sh
cd web2
npm install
npm run build      # gen scenario + build BOTH wasm (kernel w/ wasm-abi-stats) + engine
npm run dev        # open the printed URL, click "Run benchmark"
```

`npm run gen` regenerates the dataset (`--n`, `--grid`, `--jitter` flags). The kernel wasm
is built with the `wasm-abi-stats` feature so the harness can report boundary-crossing
eval counts.

## What we found, and what we did about it

### The diagnosis (before)

Measured on this scenario (Opus dev box, release wasm):

| stage | basalt (3000 pts) | sediments (9000 pts) | scaling |
|-------|------------------:|---------------------:|---------|
| fit (cokriging solve) | 1.7 s | **34.6 s** | ~N³ (dense matrix factor) |
| per-sample eval | 27 µs | 81 µs | ~N (predictor sum over weights) |

The bottleneck was the cokriging kernel at 9000 surface points, **not** the two-wasm split
(the boundary crossing is tens of ns — negligible against an 81 µs eval). Crucially, an
eigenvalue analysis showed the matrix was both huge AND **rank-deficient**: cond ~4.5e8
with ~70% near-zero eigenvalues. The 9000 borehole points were massively **oversampled** —
only a few hundred carry independent information. That single fact caused both the slow
fit (N³) and the ill-conditioning.

### The fix: residual-guided decimation (a kriging coreset)

`KernelOptions.decimate` (wired through the ABI as `decimate_frac`): seed a coarse subset,
then re-add only the points the coarse field mis-predicts by more than `frac · (isovalue
range)` — the fold hinges / anomalies — and iterate. Redundant points in flat clusters
have ~zero residual and stay out. **The data is honored to a tolerance, not subsampled.**
`decimate_frac = NaN` keeps all points (gempy bit-exact, the validation-suite default).

### The result (after, faulted 9000-pt sediments, through the wasm ABI)

| stage | full | decimated (frac 0.2) | speedup |
|-------|-----:|---------------------:|---------|
| **fit** | 34.8 s | **0.57 s** | **61×** |
| **per-sample eval** | 82 µs | **6.8 µs** | **12×** |

Field agreement vs the full fit: RMS ~1% of the field scale. Decimation kept ~250 of 3000
points on the basalt block — exactly the informative rank the eigenvalue analysis
predicted. Because eval is linear in kept-point count, decimation fixed the **mesh** cost
for free too (no SIMD / batching needed): a depth-6 mesh drops from ~20 s to ~1–2 s.

**Why not tensorken / a tensor backend / matrix-free GMRES?** All investigated and
rejected: tensorken is a teaching NN lib with no solver; gempy's tensor backend
accelerates the *eval* (PyKeOps), not the solve, and caches the solve anyway; matrix-free
iterative can't bit-match gempy on this rank-deficient system (the solution is non-unique).
Decimation is what the linear algebra was demanding. (See the kernel commit and memory.)

## Files

- `gen/generate_scenario.py` — the dataset generator (no deps beyond the stdlib).
- `src/main.ts` — the browser harness (fit timing, depth sweep, tris/verts/eval table).
- reuses `../web/src/kernel-bridge.ts` (the memory-bridge + kernel instance) via a Vite
  alias; the engine wasm is built into `src/wasm/`, the kernel into `public/`.
