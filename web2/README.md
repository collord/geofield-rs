# web2 — two-wasm scale benchmark

A throughput harness for the two-wasm split (EUPL kernel + BSD engine) on a realistic
faulted, multi-series scenario at borehole scale. It loads both wasm modules, fits the
stack across the module boundary, and times fit + octree meshing while counting the
per-sample `gf_eval` calls that cross the boundary.

## The scenario

Generated by `gen/generate_scenario.py` (oldest → newest):

- **3 intact sedimentary contacts** (~400 ft apart, gently undulating) — one conformable
  series, 3 interface ids / 4 lithology units.
- an **erosional surface** dipping ~10° with **basalt** filling above it — a younger
  *Erode* series.
- a **late fault** (strike 20°, dip 80°, **100 ft down-to-the-east**) applied to both
  series (it post-dates everything).
- **3000 vertical boreholes** on a 300 ft grid jittered by N(0, 40 ft), each logging every
  contact it crosses → ~9000 sediment + ~3000 basalt surface points.

> Scale note: 3000 holes on a *literal* 300 ft grid is only 100 holes (a 3000 ft square).
> To honor the 3000-hole target the generator sizes the map to ~16,500 ft and rescales the
> geology to fit (the absolute 400 ft thickness / 100 ft offset are preserved).

## Run

```sh
cd web2
npm install
npm run build      # gen scenario + build BOTH wasm (kernel w/ wasm-abi-stats) + engine
npm run dev        # open the printed URL, click "Run benchmark"
```

`npm run gen` regenerates the dataset (`--n`, `--grid`, `--jitter` flags). The kernel wasm
is built with the `wasm-abi-stats` feature so the harness can report boundary-crossing
eval counts.

## What we found (headline)

Measured on this scenario (Opus dev box, release wasm):

| stage | basalt (3000 pts) | sediments (9000 pts) | scaling |
|-------|------------------:|---------------------:|---------|
| fit (cokriging solve) | 1.7 s | **34.6 s** | ~N³ (dense matrix factor) |
| per-sample eval | 27 µs | 81 µs | ~N (predictor sum over weights) |

**The bottleneck is the cokriging kernel at 9000 surface points, not the two-wasm split.**

- **Fit** factors a dense (N + constraints)² covariance matrix *per fault block* → ~N³.
  9000 points takes ~35 s. This is identical natively; the split adds nothing here.
- **Per-sample eval** sums the cokriging predictor over all N weights → ~linear in N
  (27 µs at 3000 pts, 81 µs at 9000). The octree calls this hundreds of thousands of times
  per mesh, so mesh time = (#samples) × (per-eval cost) is dominated by the field math, not
  the wasm boundary crossing (which is tens of ns — negligible against an 81 µs eval).

**Implication:** the per-sample-cross-the-boundary design we chose for the split is *not*
the thing to optimize. The kernel itself needs either fewer surface points (decimation /
local neighborhoods) or a different solve before this is interactive at 9000-point scale.
The two-wasm boundary is essentially free relative to the cokriging cost.

## Files

- `gen/generate_scenario.py` — the dataset generator (no deps beyond the stdlib).
- `src/main.ts` — the browser harness (fit timing, depth sweep, tris/verts/eval table).
- reuses `../web/src/kernel-bridge.ts` (the memory-bridge + kernel instance) via a Vite
  alias; the engine wasm is built into `src/wasm/`, the kernel into `public/`.
